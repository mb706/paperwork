**I recommend Rust→WASM for the entire authoritative simulation, with moderate confidence.** Keep TypeScript for the data stage, worker shell, networking, renderer and UI. Use one simulation thread. Avoid splitting mutable simulation systems between languages: the coupled hot core makes a later port a substantial rewrite.

The three strongest arguments for Rust are:

1. **Performance headroom.** The measured core is approximately 1.35–1.7× faster across browsers; Node megabase time falls from 5.95 to 3.46 ms. Catch-up depends on excess throughput, `R − 60`, so this margin becomes especially valuable near the 60 UPS limit.
2. **More predictable execution.** The V8 deoptimisation problem demonstrates a real maintenance cost of performance-sensitive JavaScript. WASM removes much speculative optimisation uncertainty, although it still has compilation tiers. This matters when rarely exercised paths first appear hours into a game.
3. **Stronger implementation guardrails.** Explicit integer types, checked indexing, ownership and exhaustive enums can catch agent mistakes before review. A single WASM binary also narrows cross-browser numeric variation. These benefits require disciplined modules and typed handles; a giant `World` indexed by interchangeable integers forfeits much of them.

The three strongest arguments for TypeScript are:

1. **Lower feature-development cost.** Across roughly 150k lines, inventories, statistics, recipes, tooltips and debugging repeatedly cross the simulation boundary. One language avoids schema coordination, generated-view maintenance and duplicated representations. Cheap memory access does not establish cheap feature development.
2. **Faster, simpler iteration.** TypeScript offers direct browser debugging and shorter builds. Rust’s reported 1–3 second incremental loop is promising, but the synthetic crate understates uncertainty at project scale; approximately 67-second release processing should stay outside routine iteration. WASM traps also complicate diagnosis and recovery.
3. **It remains technically viable.** The study establishes no TypeScript performance failure, and disciplined TypeScript reproduced the tested results across engines. D1–D20 address the dominant desync causes—ordering, incomplete saves and impure caches—in either language. Rust does not make those problems disappear.

The study supports the kernel ranking more strongly than its product forecasts.

**Kernel equivalence looks reasonably fair.** I inspected the corresponding storage, update loops and arithmetic; mirroring the V8 fix in Rust is appropriate. An additional seed matched TypeScript, WASM and NO_SLEEP hashes **every tick for 6,600 ticks in all four regimes**. However:

- **Clock pairing does not automatically cancel drift.** [tables.ts](/home/mewse/browsergame/design/engine-study/harness/tables.ts:76) includes turbo runs in ratios despite sequential, fixed-order execution. Chrome Mid/backed contains a 1.26× pair with turbo TypeScript and base-clock WASM; its base-clock pairs average approximately 1.52×. Node’s speed-based turbo classification is circular. Two-second CPU0 samples and whole-run maxima cannot establish the frequency during each timed window; `scaling_cur_freq` itself has documented limitations. Randomise or alternate order and measure frequency during timing. [CPUFreq documentation](https://www.kernel.org/doc/html/latest/admin-guide/pm/cpufreq.html)
- **The workload is narrow.** Repeated cells, nine item types, fixed topology and no construction churn omit important locality, allocation and graph costs. Megabase measurements cover Node/native, not browsers. Host-to-laptop factors remain uncalibrated. Extrapolating the kernel’s speedup across the entire simulation is unjustified: if only the estimated 37% improved by 1.6×, total improvement would be approximately 16%.
- **Matching hashes establish agreement on tested states, not correctness or equal work generally.** Campaign hashes are endpoint checks; shared physics bugs can survive. Save/join equivalence, action fuzzing and D18’s per-tick cross-engine traces remain essential.
- **Boundary and productivity evidence is incomplete.** The [UI-query responses](/home/mewse/browsergame/design/engine-study/harness/web/src/worker.ts:117) contain fabricated inventory and technology data. The arena experiment measures array access, not evolving UI contracts. A successful mechanical port and 28 cloned kernels do not establish months-long agent productivity.
- **Tail claims need qualification.** Firefox recompilation is a hypothesis; NUMA attribution needs tracing evidence. “No JIT stalls” overstates WASM’s guarantees: V8 still compiles and tiers WASM. Cold measurements also precompile/instantiate WASM before the measured workload. Zero tick-window GC does not guarantee an allocation-free worker shell. [V8 compilation pipeline](https://v8.dev/docs/wasm-compilation-pipeline)

Also, multiplayer §3.6 disconnects slow clients by default; they set everyone’s pace only under the optional matching policy.

If Rust is chosen, these are the five most important boundary rules:

1. **Rust owns authoritative state and rules.** Closures enter through one validated tick API. Queries, extraction and TypeScript views cannot mutate simulation state or influence future results.
2. **Generate contracts from one schema.** Generate action codecs, prototype records, read views and saved/derived annotations. Specify widths, units, IDs, ordering and versions; never expose Rust’s incidental object layout.
3. **Expose bulk projections and subscriptions.** Build inventory panels, statistics and render packets through reusable adapters. Avoid per-entity FFI calls and duplicated gameplay calculations in TypeScript. Preserve the existing main-thread mirror and pooled transferables.
4. **Make view lifetimes explicit.** Only worker-side adapters access linear memory. Reacquire views after memory growth or pool relocation; never retain pointers across invalidating calls. [Memory-growth specification](https://www.w3.org/TR/wasm-js-api-2/#memories)
5. **Make the boundary reviewable and testable from M0.** Demonstrate real inventory/statistics screens, save/load, structured errors and trap recovery. Run native tests plus browser replay/join traces; recover multiplayer through snapshots and closure replay.
