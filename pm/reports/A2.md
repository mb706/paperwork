# A2: Multiplayer architecture
Status: done

## Summary

`design/multiplayer/DESIGN.md` is a complete, implementable multiplayer design. It covers the brief's ten points, each with its own section, and every number is either measured in a proof of concept on this host or cited (40 sources in Appendix A).

**The architecture in brief.**
- **Model.** Deterministic lockstep, as Factorio does it: every client runs the whole simulation and only input actions travel.
- **Sequencing.** A small relay owns the tick clock and never simulates. Clients stamp each action with the tick they expect it to run in (estimated relay tick plus an adaptive margin). The relay accepts on-time actions, moves late ones to the open tick, and broadcasts each closed tick's action list. This is Factorio's scheme from FFF-302; it makes local prediction exact.
- **No host.** Without a host there is nothing to migrate, and rooms (snapshot plus tick log on the relay) outlive their players.
- **Transport.** WebSocket over TLS on 443, same origin as the site: one control socket and one bulk socket.
- **No NAT hole punching.** From a browser it exists only as WebRTC/UDP, which the user's network (LRZ's Secomat: automatic host blocking on scan-like flow patterns, documented) penalises. Even native hole punching fails for about 30% of attempts, and with a relay sequencer it would not shorten the critical path.
- **Joining.** A donor client serializes after a sequenced marker tick. The relay pipes the snapshot through (paced, LEDBAT-style, so the donor's own game does not lag) and caches it. The joiner fast-forwards the buffered ticks.
- **Desyncs.** A per-tick digest plus a rotating slice hash, reported every 30 ticks with an epoch, decided by majority vote. Repair is a background re-sync: a shadow simulation in a second worker catches up and is swapped in. A page-delta variant is recommended.
- **Determinism.** D1–D20 is a checklist for M0, each rule with its enforcement. S1–S14 are the engine seams; single player is multiplayer with a `LocalSequencer`.

**Proof of concept.** `design/multiplayer/poc/` holds about 2,200 lines of JavaScript, with `ws` 8.22.0 as the only dependency:
- a relay;
- a lockstep client that runs in Node and in a browser worker;
- a toy deterministic simulation;
- a userspace impairment proxy (delay, jitter, loss as head-of-line stalls, a shared FIFO bottleneck, drops, black-holes);
- a scenario runner with 10 scenarios, a relay load generator, and a raw-CDP hidden-tab experiment in Chrome.

How to run it is in DESIGN §12.1.

## Decisions and deviations

1. **The relay sequences, not a hosting client** (brief point 1 left both open). The constraint allows sequencing, the relay never sleeps, and host migration disappears as a problem.
2. **Clients stamp target ticks; the relay arbitrates.** Measured against relay-side stamping on identical links (DESIGN §3.4, §12.2): client stamping mispredicted only late actions (0–5%); relay stamping mispredicted 15–54% of walk inputs in the final run.
3. **No NAT hole punching, no WebRTC, no WebTransport in version 1** (brief point 2): §2.1–§2.3. WebTransport stays a possible opt-in later. It is never probed automatically, because a QUIC probe could trip a firewall like the user's.
4. **Spec 10 §4.4's single `World.player` becomes `players[]`** (seam S1), and the save's `PLAYER` section becomes `PLAYERS`. A proposed change to 10, for Phase B.
5. **Stricter than 10 §4.1: ban `**` and `Math.pow` entirely** (D5). ECMA-262 makes `Number::exponentiate` implementation-approximated for every exponent, and V8 constant-folds `**` differently from `Math.pow`. Also: no NaN in saved state (D6), because engines may choose NaN bit patterns in typed arrays.
6. **10 §8.5's input log becomes the closure log** (S8), so replays, bug bundles and multiplayer share one format.
7. **10 §3.3 and 07 §19.3:** in multiplayer the game never pauses on a hidden tab, and the simulation worker is driven by arriving ticks rather than timers (measured, §12.5). Single player is unchanged.
8. **Chat is out of band** in multiplayer, unlike Factorio's `write_to_console` input action (I §8.2): it keeps working while paused and stays out of input logs. Console *commands* that change the world remain actions.
9. **Selection is presence, not simulation state** (Factorio sends it as input actions; FFF-302's megapacket bug came from that). The UI result is ISO: other players' coloured selection rectangles, as in 2.0.33.
10. **Client autosaves on by default** (Factorio's `autosave_only_on_server` is true), because our relay cannot save without a donor and any player must be able to re-host.
11. **Remote cursors proposed as a BEND, off by default**, and listed as a question for the user.
12. **The PoC is JavaScript (`.mjs`), not TypeScript**: no build step, and it runs in Node and the browser unchanged. Production code follows 10 §2 (TypeScript 7, Vite, Vitest).
13. **The PoC client runs networking in the simulation's thread**, except for the shadow worker. That is deliberately simpler than the design, and two of the PoC's measurements are about exactly that difference (§12.3, §12.4).
14. **Player-facing strings are only proposals** (DESIGN §8.4), for 08's owner, as `pm/README.md` requires.

## Verification

All runs on CPUs 8–15 (`taskset -c 8-15`), as instructed. The PoC found five problems in its own first versions, and each became a rule in the design:
1. The relay's digest comparison expected only players whose last `STATUS` had passed the tick, so the fastest client was compared against nobody. Rule: expect every live player, with a 5-s timeout (DESIGN §5.1).
2. Stale digests from a client that is being re-synced triggered four re-syncs for one desync. Rule: digest epochs, and purge on re-sync (§5.1).
3. The first margin controller added each action's lateness and decayed one tick per 5 s. One loss stall left 18–20 ticks of input delay for a minute. Rule: margin = a high percentile of recent need (§3.4).
4. The first playout controller recomputed the buffer from scratch every second, undoing each underrun's widening. Rule: grow at once, shrink slowly (§3.6).
5. Time-slicing the re-sync's shadow simulation on the live thread saturated it at late-game tick costs (control RTT of 1–4.6 s; the re-sync never finished). Rule: the shadow in its own worker. With a worker the late-game re-sync completed (§12.6).

**Commands.**
- `taskset -c 8-15 node run-scenarios.mjs base relaystamp hz30 mixed harsh slow bigjoin bigjoin-paced bigresync bigresync-paced`: about 15 minutes. Then `node summarize.mjs` (tables in `results/summary.md`).
- `taskset -c 8-15 node loadgen.mjs --rooms 1|10|50|100`.
- `xvfb-run -a taskset -c 8-15 node browser/hidden-tab-cdp.mjs 390`.
- `npx @biomejs/biome@2.5.15 lint` on the PoC (clean); `node --check` on every file.

## Open issues and follow-ups

1. **User decisions** (DESIGN §11): where to host the relay (VPS or Cloudflare), whether to store games server-side, the policy for a slow machine (drop, or slow everyone), remote cursors, starting items for new players, the player cap.
2. **Phase B:** fold S1–S14 and D1–D20 into `10-architecture.md` (the list is at the end of DESIGN §7), and add the multiplayer milestone to 10 §12. M0 needs S1–S10, S12, S14 and the D18 tests.
3. **Spec owners:**
   - 08: the strings of DESIGN §8.4;
   - 07, 04 and 08: the multiplayer variants of per-player text (queue bylines, the run report's hand-crafted line, per-player achievements);
   - 10 §5.1: the rules for offline characters and the hand on leaving.
4. **Not prototyped:**
   - the latency state (only its prerequisite, exact prediction, is measured);
   - delta re-sync by page hashes;
   - the net worker in the browser;
   - the Cloudflare Durable Object adapter (its timers and clock need checking: `Date.now()` advances only after I/O there);
   - a tuned LEDBAT (the PoC's crude one stretches transfers by roughly half to double).
5. **Hidden-tab behaviour in Firefox and Safari is unmeasured on this host.** Firefox's source shows release builds do not throttle worker timers but Nightly does. Add the hidden-tab check to `bench.html` and run it on the user's machine (DESIGN §9 item 7).
6. **WP A1's language choice** changes only D19 and the size of the float-divergence risk (DESIGN §1.4). The design holds for either.
7. **The PoC does not prove cross-engine determinism of the real engine.** That is D18(d)'s nightly job once code exists.
